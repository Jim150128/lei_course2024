## 三、踩坑与解决记录（重点）

> 本次作业最大的收获，不只是装好了环境，更是一段「查资料 → 反复试错 → 再查 → 终于成功」的真实排障经历。

### 🔥 3.1 虚拟网卡配置 —— 全过程中最艰难的一环

**问题现象：**

- 虚拟机安装后**无法上网**：`ping` 网关与外网均不通；
- 宿主机与虚拟机之间无法互通，导致 **PuTTY 根本无法连接**，SSH 任务一度被卡住；
- VMware「虚拟网络编辑器」中 VMnet8 状态异常，网络服务表现不稳定。

**排障过程（前后约两天，极其曲折）：**

| 阶段 | 求助来源 | 采取的做法 | 结果 |
| --- | --- | --- | --- |
| 第 1 轮 | 各种 AI 工具 | 按 AI 给出的方案反复切换 NAT / 桥接、手动填写 IP | ❌ 不同 AI 说法不一（有的让改桥接、有的让改 NAT），照做后依然不通，甚至把网卡配置改得更乱 |
| 第 2 轮 | CSDN 教程 | 先后阅读十余篇图文教程，逐条对照设置子网、网关与 DHCP | ❌ 多数教程版本较旧，菜单界面与我的 VMware / Ubuntu 版本对不上，配置后依旧无法联网 |
| 第 3 轮 | B 站视频 | 找到与所用版本完全匹配的实操视频，逐帧暂停对照操作 | ✅ **终于找到真正原因并彻底解决** |

**最终找到的“病根”与解决办法（来自 B 站视频）：**

1. **VMware 的 NAT / DHCP 服务没有正常运行**：在 Windows 服务管理中手动重启了 `VMware NAT Service` 与 `VMware DHCP Service`；
2. **虚拟网卡被此前的反复修改弄乱**：在「虚拟网络编辑器」中执行**恢复默认设置**，重建 VMnet8（NAT）后再设置子网网段；
3. **虚拟机内 IP 与 NAT 网段不一致**：按视频统一网段后，Ubuntu 端改用自动获取（DHCP），网络立即恢复；
4. 验证链路：`ping 网关 → ping 宿主机 → ping 外网 → PuTTY SSH 连接`，全部通过。

**这段经历给我的体会：**

- 排障时**软件版本匹配**非常关键，老教程不一定适用于新版本；
- 同一问题出现多种答案时，要结合自己的实际现象判断，不能盲目照抄；
- B 站视频能完整展示操作路径与界面，比零散图文更适合新手复现；
- 本次用到的工具链：**各种 AI（多轮提问比对）→ CSDN（十余篇图文）→ B 站（最终方案）**，虽然过程艰难，但坚持排查总能解决。

### ⚙️ 3.2 配置 Codex 的困难 —— 第二道坎

**困难表现：**

- Codex 依赖的 Node.js 等运行环境需要与本机逐一核对；
- 登录与鉴权环节反复出现异常，网上教程版本各异、说法不一；

**解决过程：**

1. 先查阅**官方文档**，确认当前版本的安装与配置步骤；
2. 遇到报错后，将完整错误信息交给**各种 AI** 帮助比对、解释，再结合官方说明判断；
3. 反复核对环境变量与配置文件，重启终端逐项验证；
4. 最终**配置成功**，Codex 可以正常运行——本清单的逐项核对与排版整理也借助了 Codex，既验证了工具环境可用，也体现了主动学习新工具的态度。
